# Контракты HTTP API K.Alert

Документ фиксирует согласованные на 24.11.2026 контракты первой версии. Это целевое поведение API, а не утверждение о готовой реализации.

Связанные документы: [требования](02-requirements.md), [архитектура](03-architecture.md), [модель данных](04-data-model.md). Наглядное представление: [доска Miro](https://miro.com/app/board/uXjVEKoWAqc=/).

## Общие правила

- Базовый путь — `/api/v1`. Все пути ниже указаны вместе с ним.
- Имена JSON-полей — `camelCase`. Перечисления передаются строками, например `"Owner"` и `"Member"`.
- Идентификаторы сущностей — UUID. `token` в маршрутах приглашений — секретный токен из ссылки, не UUID записи.
- Моменты времени передаются в ISO 8601 в UTC, например `"2026-11-23T12:00:00Z"`.
- Отсутствующее необязательное значение возвращается как `null`, если для поля явно не установлено другое поведение.
- При успехе JSON содержит `data`, `code: null`, `message: null`, `errors: {}` и `traceId`.
- Ошибка использует соответствующий HTTP-статус и JSON с `data: null`. Внутренние подробности сбоя остаются в логах.
- Успех без результата — `204 No Content`, тело отсутствует целиком. Отдельного JSON-ответа без результата нет. Ошибка такого метода всё равно возвращается в общем формате ошибки.
- Параметры пути обязательны. Если у метода указано отсутствие тела запроса, JSON-тело не требуется.

### Один объект

```json
{
  "data": {
    "id": "742cc23a-d8d1-4418-9b6a-115fd5778ead",
    "name": "Команда разработки"
  },
  "code": null,
  "message": null,
  "errors": {},
  "traceId": "идентификатор запроса"
}
```

### Список без пагинации

```json
{
  "data": {
    "items": []
  },
  "code": null,
  "message": null,
  "errors": {},
  "traceId": "идентификатор запроса"
}
```

Объекты находятся внутри массива `data.items`. Если список пуст, возвращается `[]`.

### Список с пагинацией

```json
{
  "data": {
    "items": [],
    "page": 1,
    "pageSize": 20,
    "totalCount": 0
  },
  "code": null,
  "message": null,
  "errors": {},
  "traceId": "идентификатор запроса"
}
```

Параметры передаются в query. Общая форма запроса (путь конкретного метода определяется отдельно):

```http
GET /api/v1/...?page=1&pageSize=20
```

| Параметр | Тип и ограничения | По умолчанию |
| --- | --- | --- |
| `page` | Целое число от 1. | `1` |
| `pageSize` | Целое число от 1 до 100. | `20` |

Поля `data.page` и `data.pageSize` возвращают применённые значения параметров. `totalCount` — количество записей после применения фильтров, до разбиения на страницы.

- Сначала применяются фильтры и сортировка, затем выбирается страница.
- Каждый метод задаёт стабильную сортировку. При совпадении основного поля дополнительный критерий — `id`.
- Если записей нет или запрошена страница за пределами списка, возвращается `200 OK`, `items: []`, запрошенные `page`, `pageSize` и фактический `totalCount`.
- При изменении фильтров или сортировки фронтенд возвращается на первую страницу.
- При параллельном добавлении или удалении записей состав страниц может меняться. Снимок списка между запросами не сохраняется.
- Некорректные значения не исправляются автоматически. Например, `page=0`, `pageSize=101`, `page=abc` возвращают `400 validation_error` с ошибкой соответствующего поля.
- Списки команд, участников и приглашений остаются без пагинации. Применение к напоминаниям и истории определяется при согласовании этих методов.

### Ошибка

```json
{
  "data": null,
  "code": "validation_error",
  "message": "Проверьте заполненные поля",
  "errors": {
    "name": [
      "Введите название команды"
    ]
  },
  "traceId": "идентификатор запроса"
}
```

| Поле | Смысл |
| --- | --- |
| `data` | При ошибке всегда `null`. |
| `code` | Стабильный машинный код для фронтенда. |
| `message` | Понятное сообщение пользователю. |
| `errors` | Объект с именами полей и массивами сообщений. При отсутствии ошибок по полям — `{}`. |
| `traceId` | Идентификатор запроса для поиска в серверных логах. |

HTTP-статусы не заменяются на `200` при ошибках. В таблицах методов перечислены согласованные ожидаемые ошибки. Непредвиденный внутренний сбой возвращается как `500` в общем формате без технических подробностей; машинный код — `internal_error`.

### Общие ошибки авторизации и сервера

| HTTP | `code` | `message` | Условие |
| --- | --- | --- | --- |
| 409 | `email_already_exists` | Этот email уже зарегистрирован | Регистрация с занятым email. |
| 401 | `invalid_credentials` | Неверный email или пароль | Неверные учётные данные при входе. |
| 401 | `unauthorized` | Необходимо войти в сервис | Нет действующего сеанса для защищённого метода. |
| 500 | `internal_error` | Не удалось выполнить запрос. Попробуйте позже | Непредвиденный внутренний сбой. |

У этих ошибок `data: null`, `errors: {}`, `traceId` содержит идентификатор запроса. Проверка отдельных полей возвращает `400 validation_error` с заполненным `errors`. Отсутствие сеанса при logout само по себе не является ошибкой.

## Проверка имени, email и секретных токенов

### Отображаемое имя

- `displayName` обязательно; от 1 до 100 символов после удаления пробелов по краям.
- Допускаются любые печатные символы, включая кириллицу и пробелы; внутренние пробелы сохраняются.
- Переносы строк и управляющие символы не допускаются. Уникальность имени не требуется.
- Нарушение возвращает `400 validation_error` с ошибкой поля `displayName`.

### Email

- Обязателен; не более 254 символов после удаления пробелов по краям.
- Пробелы по краям удаляются при регистрации и входе.
- Принимается один корректный адрес без отображаемого имени: `dmitry@example.com`, а не `Дмитрий <dmitry@example.com>`.
- Поиск и уникальность не учитывают регистр.
- Точки и часть после `+` не удаляются: `name+work@example.com` сохраняется как отдельный адрес.
- Некорректные данные возвращают `400 validation_error` с ошибкой поля `email`.

### Секретные токены

Один формат применяется к секретным токенам `UserSession`, `TeamInvitation` и `TelegramChatConnectionRequest`. Каждый токен создаётся независимо.

| Параметр | Значение |
| --- | --- |
| Генерация | 32 криптографически случайных байта. |
| Представление | Base64url без завершающих `=`. |
| Длина строки | 43 символа. |
| Допустимые символы | `A–Z`, `a–z`, `0–9`, `_`, `-`. |
| Регистр | Учитывается. |
| Пробелы | Не допускаются, автоматически не удаляются. |
| Хранение | Только хеш в соответствующей таблице. |

API проверяет длину, набор символов и корректность декодирования в 32 байта. Для токена приглашения неправильный формат означает `400 validation_error`, корректный формат без совпадения в БД — `404 invitation_not_found`. Некорректный токен сеанса в cookie означает отсутствие действующего сеанса, с учётом отдельного правила повторного logout.

Токены ASP.NET Core Antiforgery сохраняют стандартный формат; ограничение 43 символа к ним не относится. Значения секретов в примерах — условные обозначения, реальные значения должны соответствовать формату выше.

## Сеансы и авторизация

Серверные сеансы хранятся в общей PostgreSQL и доступны всем экземплярам API. Cookie содержит случайный секретный токен; БД хранит его хеш в `UserSession.TokenHash`. `UserSession.Id` сам по себе не даёт доступа.

Интерфейс и пользовательский API размещаются на одном origin: например, `https://kalert.example` и `https://kalert.example/api/v1`. Домен в примере условный.

| Параметр | Cookie сеанса | Служебная cookie Antiforgery |
| --- | --- | --- |
| Имя | `__Host-kalert-session` | `__Host-kalert-csrf` |
| Содержимое | Случайный секретный токен сеанса | Cookie-токен стандартного Antiforgery |
| `HttpOnly` | `true` | `true` |
| `Secure` | `true` | `true` |
| `SameSite` | `Lax` | `Strict` |
| `Path` | `/` | `/` |
| `Domain` | Не задаётся | Не задаётся |
| Срок | 7 дней, как у серверного сеанса | Управляется стандартным механизмом Antiforgery |

Браузер автоматически отправляет cookie. JavaScript не читает их содержимое. Проверочный CSRF-токен фронтенд получает из JSON отдельного метода.

Сеанс действует 7 дней с момента входа без автоматического продления. Закрытие браузера его не завершает. Разные устройства имеют отдельные сеансы. Повторный вход из авторизованного браузера отзывает прежний сеанс этого браузера. Истёкший или отозванный сеанс не допускает вызова защищённых методов.

Пароль содержит от 8 до 128 символов после удаления пробелов по краям. Эта обработка выполняется и при регистрации, и при входе. Внутренние пробелы сохраняются, регистр учитывается. Обязательных требований к цифрам, заглавным буквам и спецсимволам нет; допускаются кириллица, пробелы, вставка из буфера и менеджеры паролей. Периодическая смена не требуется. API повторно проверяет входные данные. В БД сохраняется только хеш пароля, сам пароль не попадает в логи.

Поля ответа пользователя:

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | string, UUID | Идентификатор профиля. |
| `displayName` | string | Отображаемое имя. |
| `email` | string | Адрес учётной записи. |

### Получить CSRF-токен

`GET /api/v1/auth/csrf`

**Доступ:** без авторизации и с действующим сеансом.

**Запрос**

Тело запроса отсутствует.

**Успешный ответ — 200 OK**

```json
{
  "data": {
    "csrfToken": "проверочный-токен"
  },
  "code": null,
  "message": null,
  "errors": {},
  "traceId": "идентификатор запроса"
}
```

API использует стандартный ASP.NET Core Antiforgery, устанавливает служебную cookie `__Host-kalert-csrf` и возвращает проверочный токен. Ответ не кешируется. Метод не требует CSRF-заголовка.

### Правила проверки CSRF

1. При открытии приложения фронтенд вызывает `GET /api/v1/auth/csrf` и сохраняет `data.csrfToken` в памяти.
2. Передаёт этот токен в заголовке `X-CSRF-Token` всех пользовательских `POST`, `PATCH`, `PUT`, `DELETE`, включая регистрацию, вход и выход.
3. После успешной регистрации, входа и выхода получает токен заново.

Проверка требуется и для logout без действующего сеанса: само отсутствие сеанса не является ошибкой, но не отменяет CSRF-проверку. GET-запросы не меняют бизнес-данные. Вебхук Telegram и служебный API обработчиков используют отдельные механизмы проверки и не требуют пользовательского CSRF-токена.

Если токен отсутствует или не прошёл проверку, действие не выполняется. Возвращается `403 Forbidden`:

```json
{
  "data": null,
  "code": "csrf_validation_failed",
  "message": "Не удалось проверить запрос. Обновите страницу и повторите действие",
  "errors": {},
  "traceId": "идентификатор запроса"
}
```

Эта ошибка применяется ко всем пользовательским методам изменения данных и дополняет таблицы ошибок ниже. Все экземпляры API используют общие ключи Antiforgery, которые сохраняются при перезапуске.

### Регистрация

`POST /api/v1/auth/register`

**Доступ:** без авторизации.

**Запрос**

```json
{
  "displayName": "Дмитрий",
  "email": "dmitry@example.com",
  "password": "ExamplePass123"
}
```

**Успешный ответ — 201 Created**

```json
{
  "data": {
    "id": "742cc23a-d8d1-4418-9b6a-115fd5778ead",
    "displayName": "Дмитрий",
    "email": "dmitry@example.com"
  },
  "code": null,
  "message": null,
  "errors": {},
  "traceId": "идентификатор запроса"
}
```

**Ошибки**

| HTTP | `code` | Условие |
| --- | --- | --- |
| 400 | `validation_error` | Некорректные входные данные. |
| 409 | `email_already_exists` | Email уже занят. |

**Правила**

- Поля `displayName`, `email`, `password` обязательны. Правила имени и email приведены в разделе «Проверка имени, email и секретных токенов».
- Уникальность email и поиск при входе не учитывают регистр.
- Профиль и учётная запись создаются в одной транзакции; уникальность email обеспечивает БД, включая параллельные регистрации.
- Регистрация сразу выполняет вход. Cookie устанавливается через `Set-Cookie`; секретный токен не возвращается в JSON.
- Поле подтверждения пароля проверяется фронтендом и не передаётся в API.


**Успешный ответ — 200 OK**

```json
{
  "data": {
    "id": "742cc23a-d8d1-4418-9b6a-115fd5778ead",
    "displayName": "Дмитрий",
    "email": "dmitry@example.com"
  },
  "code": null,
  "message": null,
  "errors": {},
  "traceId": "идентификатор запроса"

```

**Ошибки**

| HTTP | `code` | Условие |
| --- | --- | --- |
| 400 | `validation_error` | Некорректные входные данные. |
| 401 | `invalid_credentials` | Неверный email или пароль. |

**Правила**

- При успешном входе создаётся сеанс и устанавливается cookie через `Set-Cookie`.
- При неверных учётных данных общее сообщение — «Неверный email или пароль», без указания, какое поле не совпало.

### Выход

`POST /api/v1/auth/logout`

**Доступ:** действующий сеанс не обязателен; метод завершает текущий сеанс браузера, если он существует.

**Запрос**

Тело запроса отсутствует.

**Успешный ответ — 204 No Content**

Тело ответа отсутствует.

**Правила**

- Текущий сеанс отзывается на сервере, cookie удаляется.
- Сеансы других устройств сохраняются.
- При отсутствующем, истёкшем или уже отозванном сеансе удаляем cookie, если она есть, и возвращаем `204`.
- Если из-за сбоя сервера нельзя подтвердить отзыв существующего сеанса, возвращаем ошибку; интерфейс не показывает успешный выход.

## Команды

Объект команды содержит `id` (UUID), `name` (строка), `createdAt` (UTC), `currentUserRole` (`Owner` или `Member`). Последнее поле вычисляется из участия текущего пользователя, в модель `Team` не добавляется.

## Участники команды

Параметр `teamId` — UUID команды, `userId` — UUID пользователя, чьё участие изменяют. Объект участника содержит `userId`, `displayName`, `role` и `joinedAt`. Email в него не включается.

## Приглашения

Приглашение одноразовое, действует 7 дней с момента создания и добавляет пользователя с ролью `Member`. `invitationId` — UUID записи, `token` — секретный токен ссылки.

Статус вычисляется по полям модели, отдельное поле в БД не требуется:

| Статус | Значение |
| --- | --- |
| `Active` | Не принято, не отозвано, срок не истёк. |
| `Accepted` | Принято, записаны принявший пользователь и время. |
| `Revoked` | Отозвано до принятия. |
| `Expired` | Не принято и не отозвано, срок истёк. |

Принятие и отзыв взаимоисключающие. Само наступление `ExpiresAt` не меняет уже принятое приглашение на `Expired`.

### Подтвердить подключение с тестовой отправкой

`POST /api/v1/teams/{teamId}/telegram-chat-connection-requests/{requestId}/confirm`

**Доступ:** инициатор запроса, который по-прежнему является Owner указанной команды.

**Запрос**

Тело запроса отсутствует. Требуется `X-CSRF-Token`.

**Успешный ответ — 200 OK**

```json
{
  "data": {
    "channelId": "742cc23a-d8d1-4418-9b6a-115fd5778ead"
  },
  "code": null,
  "message": null,
  "errors": {},
  "traceId": "идентификатор запроса"
}
```

Возвращается идентификатор канала, карточку которого может открыть интерфейс. Контракт получения самого канала обсуждается отдельно.

**Порядок выполнения**

1. API проверяет команду, инициатора запроса и его текущую роль.
2. Для уже завершённого запроса возвращает сохранённый `channelId` без новой тестовой отправки.
3. Для незавершённого запроса проверяет срок действия и наличие выбранной группы.
4. Отправляет тестовое сообщение в Telegram.
5. После успешной отправки в одной транзакции создаёт канал или связывает запрос с существующим неудалённым каналом и заполняет `CompletedAt`, `ChannelId`.

Новый канал становится активным. Если чат уже подключён, возвращается существующий канал. Отключённый канал автоматически не включается: владелец включает его отдельно.

**Повторы и сбои**

- Одновременные подтверждения одного запроса выполняются последовательно между всеми экземплярами API.
- Повтор завершённого запроса возвращает тот же `channelId`, даже после наступления `expiresAt`, пока запись запроса сохраняется.
- При ошибке тестовой отправки запрос остаётся незавершённым. Проверку можно повторить до истечения 15 минут с момента создания запроса.
- Если тестовое сообщение отправлено, а результат не сохранился, повтор может отправить сообщение ещё раз.
- После удаления запроса ежедневной очисткой возвращается `404 connection_request_not_found`.

**Ошибки**

| HTTP | `code` | Условие |
| --- | --- | --- |
| 400 | `validation_error` | Некорректные идентификаторы. |
| 401 | `unauthorized` | Нет действующего сеанса. |
| 403 | `forbidden` | Пользователь не является инициатором запроса или больше не имеет роли Owner. |
| 403 | `csrf_validation_failed` | Ошибка проверки CSRF. |
| 404 | `team_not_found` | Команда не существует или вызывающий пользователь в ней не состоит. |
| 404 | `connection_request_not_found` | Запрос не найден в указанной команде. |
| 409 | `chat_not_selected` | Группа ещё не выбрана. |
| 410 | `connection_request_expired` | Незавершённый запрос истёк. |
| 422 | `telegram_chat_unavailable` | Telegram явно сообщил, что бот не может отправлять в эту группу. |
| 503 | `telegram_temporarily_unavailable` | Временная ошибка Telegram, ограничение частоты или тайм-аут. |

Ошибки Telegram возвращаются с понятным сообщением без секретных данных. Непредвиденные внутренние сбои возвращаются как `500 internal_error`. Все ошибки используют общий JSON-формат.

## Что ещё не согласовано

Следующие пункты не являются готовыми контрактами:

- Конкретные методы с пагинацией, их фильтры и сортировки; общие параметры `page` и `pageSize` согласованы выше.
- API управления каналами, напоминаниями и историей, служебный API обработчиков доставок. Создание запроса подключения Telegram-чата, просмотр состояния и подтверждение согласованы выше; остальные HTTP-контракты обсуждаются дальше.
