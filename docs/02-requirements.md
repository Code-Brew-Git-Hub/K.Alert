# Требования к первой версии K.Alert

Цель, пользователи и границы проекта описаны в [обзоре проекта](01-project-overview.md).

## Регистрация и вход

- Пользователь может самостоятельно зарегистрироваться по электронной почте и паролю, войти и выйти из сервиса.
- После обычного входа открывается список команд пользователя. Если список пуст, сервис предлагает создать команду.
- Если пользователь открыл приглашение без активного сеанса, сервис предлагает войти или зарегистрироваться и затем возвращает его к тому же приглашению. Вступление подтверждается отдельным действием.
- Корпоративный вход предусмотрен за пределами первой версии.

### Имя и email

- Отображаемое имя содержит от 1 до 100 символов после удаления пробелов по краям. Разрешены печатные символы, включая кириллицу и пробелы. Внутренние пробелы сохраняются; переносы строк и управляющие символы не допускаются. Имя не обязано быть уникальным.
- Email обязателен, не длиннее 254 символов после удаления пробелов по краям. При регистрации и входе пробелы по краям удаляются; принимается один корректный адрес без отображаемого имени.
- Поиск и уникальность email не учитывают регистр. Точки и часть после `+` не удаляются.
- Ошибки имени и email возвращаются как `400 validation_error` с сообщениями по соответствующим полям.

### Пароль и сеанс пользователя

- Регистрация сразу выполняет вход. Пароль содержит от 8 до 128 символов после удаления пробелов по краям. Пробелы по краям удаляются и при регистрации, и при входе; внутренние пробелы сохраняются, регистр учитывается.
- Допускаются буквы, включая кириллицу, цифры, спецсимволы и пробелы. Обязательных комбинаций типов символов нет. Разрешены вставка из буфера и менеджеры паролей. Периодическая смена не требуется.
- Фронтенд и API применяют одинаковые правила; сервер повторно проверяет входные данные. Подтверждение пароля проверяется на фронтенде и в API не передаётся. В БД хранится только хеш пароля, сам пароль не попадает в логи.
- Сервер хранит сеансы в общей PostgreSQL. Cookie содержит случайный секретный токен; в БД сохраняется его хеш. Cookie использует `HttpOnly`, `Secure`, `SameSite=Lax`. Запросы, изменяющие данные, защищены от CSRF.
- Интерфейс и API размещаются на одном origin. Cookie сеанса — `__Host-kalert-session`; служебная cookie CSRF — `__Host-kalert-csrf` (`HttpOnly`, `Secure`, `SameSite=Strict`). Для обеих задан `Path=/`, `Domain` не задаётся.
- Фронтенд получает CSRF-токен через `GET /api/v1/auth/csrf`, хранит его в памяти и передаёт в `X-CSRF-Token` пользовательских запросов изменения данных, включая регистрацию, вход и выход. После успешной регистрации, входа и выхода получает токен заново. При ошибке проверки действие не выполняется, API возвращает `403 csrf_validation_failed`; интерфейс предлагает обновить страницу и повторить действие.
- Сеанс действует 7 дней с момента входа без автоматического продления. Закрытие браузера не завершает сеанс. При истечении или отзыве защищённые методы возвращают `401`, интерфейс предлагает войти снова.
- Каждое устройство имеет отдельный сеанс. Вход и регистрация создают новый сеанс; повторный вход из авторизованного браузера отзывает прежний сеанс этого браузера. Выход отзывает текущий сеанс на сервере и удаляет cookie; другие устройства продолжают работать.
- Истёкшие и отозванные сеансы удаляются ежедневной очисткой. Для отозванных записей ждать окончания срока не требуется.

## Роли и права

Роль пользователя действует в пределах конкретной команды.

| Действие | Владелец | Участник |
| --- | --- | --- |
| Открывать команду и просматривать её напоминания и историю доставок | Да | Да |
| Создавать, изменять, приостанавливать, возобновлять и удалять напоминания | Да | Да |
| Создавать и отзывать приглашения, менять роли и исключать участников | Да | Нет |
| Подключать, отключать, включать и удалять каналы доставки | Да | Нет |
| Возобновлять заблокированную доставку после устранения причины | Да | Нет |
| Выйти из команды | Да, если остаётся другой владелец | Да |

Сообщение в Telegram получает любой человек с доступом к соответствующему чату. Учётная запись K.Alert для этого не требуется.

## Команды и приглашения

### Создать команду

1. Пользователь открывает раздел «Команды», нажимает «Создать команду» и вводит название.
2. Название содержит от 1 до 100 символов после удаления пробелов по краям. Одинаковые названия команд разрешены. Сервис показывает ошибку рядом с полем при нарушении ограничения.
3. После сохранения сервис назначает создателя владельцем и открывает страницу команды. Отсюда можно перейти к участникам, каналам, напоминаниям и истории доставок.

Список команд включает только команды текущего пользователя, новые первыми, без пагинации. Если команд нет, возвращается пустой список. Ответ команды содержит вычисляемую роль текущего пользователя `currentUserRole`, отдельное поле в `Team` не добавляется.

### Пригласить коллегу

1. Владелец открывает раздел «Участники», нажимает «Пригласить» и копирует одноразовую ссылку.
2. Сервис показывает срок действия ссылки. Она действует 7 дней с момента создания. Любой текущий владелец может отозвать действующее неиспользованное приглашение раньше.
3. Коллега открывает ссылку. После входа сервис показывает название команды и кнопку «Вступить в команду».
4. При подтверждении сервис повторно проверяет ссылку, добавляет пользователя с ролью «Участник», отмечает ссылку использованной и открывает страницу команды.

| Ситуация | Поведение сервиса |
| --- | --- |
| Ссылка истекла, отозвана или использована другим пользователем | Показывает причину и предлагает запросить новую ссылку у владельца. |
| Ссылка уже принята этим пользователем, и он по-прежнему в команде | Повторное принятие возвращает команду с текущей ролью. После выхода или исключения ссылка не позволяет вступить повторно. |
| Пользователь уже в команде | Предлагает открыть команду. Действующее приглашение остаётся неиспользованным. |
| Два пользователя одновременно подтверждают вступление по одной ссылке | Вступает один пользователь. Второй получает сообщение, что ссылка уже использована. |

Ссылку с секретным токеном API возвращает только при создании. Владелец может получить список всех приглашений команды без пагинации, новые первыми; в списке нет токена и ссылки. Статус `Active`, `Accepted`, `Revoked` или `Expired` вычисляется по полям приглашения.

Просмотр по секретной ссылке доступен без авторизации и показывает только название команды, срок и статус. Сам просмотр не добавляет участника и не использует ссылку. Для принятия требуется действующий сеанс.

Повторное принятие тем же пользователем возвращает команду с его текущей ролью, если он по-прежнему состоит в команде. После выхода или исключения использованная ссылка не позволяет вступить повторно. Уже состоящий в команде пользователь не использует активное приглашение.

Повторный отзыв отозванного приглашения и отзыв истёкшего не требуют изменений и возвращают успех без результата. Принятое приглашение отозвать нельзя; участник остаётся в команде. Принятие и отзыв согласованы транзакционно.

### Управлять участниками

- В разделе «Участники» владелец видит состав команды и роли. Он может назначить участника владельцем, снять роль владельца или исключить пользователя. После снятия роли владельца пользователь остаётся участником команды.
- В команде всегда остаётся хотя бы один владелец. Сервис отклоняет выход, исключение или смену роли, если это оставит команду без владельца. Правило действует и при одновременных действиях нескольких пользователей.
- После выхода или исключения человек теряет доступ к команде в K.Alert. Созданные им напоминания остаются у команды и продолжают работать по расписанию. Доступ к сообщениям в Telegram определяется доступом к чату.

Список участников доступен любому участнику команды, без пагинации, с сортировкой по времени вступления по возрастанию, затем по `UserId`. В ответе есть `UserId`, отображаемое имя, роль и время вступления; email не возвращается.

Изменять роли и исключать других участников может только владелец. Он может назначить другого владельца и понизить себя при сохранении другого владельца. Передача уже установленной роли возвращает текущие данные.

Для самостоятельного выхода используется отдельное действие. Исключение самого себя через метод исключения отклоняется. Повторный выход возвращает отсутствие команды для пользователя, поскольку участие уже прекращено.

## Каналы доставки

В первой версии команда может подключить несколько групповых чатов Telegram. Подключение действует на уровне группы целиком.

1. Владелец открывает «Каналы доставки», нажимает «Подключить Telegram-чат» и переходит по одноразовой ссылке «Выбрать чат в Telegram».
2. В Telegram владелец выбирает группу и добавляет в неё бота K.Alert. После возвращения в сервис он проверяет название выбранного чата и подтверждает подключение.
3. Бот отправляет тестовое сообщение. После успешной отправки новый чат отображается как активный канал. Если запрос связан с уже существующим отключённым каналом, канал автоматически не включается.

| Ситуация | Поведение сервиса |
| --- | --- |
| Ссылка истекла | Предлагает создать новую ссылку. |
| Бот не смог отправить тестовое сообщение | Сообщает, что подключение не завершено. Предлагает проверить право бота отправлять сообщения и повторить проверку. |
| Чат уже подключён к этой команде | Открывает существующую запись. Отключённый канал можно включить снова. |

Отключение канала прекращает создание новых заданий для этого чата. Его история остаётся доступной, а ранее созданные задания продолжают обрабатываться.

### Срок и использование ссылки подключения

Ссылка подключения чата действует 15 минут с момента создания и позволяет выбрать один чат. После выбора чат закрепляется за запросом. Инициировавший подключение владелец подтверждает выбор в K.Alert до истечения срока. API повторно проверяет его права и отправляет тестовое сообщение. При ошибке проверку можно повторить до истечения срока. После успешного подключения запрос считается использованным. Для выбора другого чата требуется новая ссылка.

Подключение хранится в `TelegramChatConnectionRequest`. Повторное подтверждение успешно завершённого запроса возвращает подключённый канал. Одновременные подтверждения создают один канал. Если тестовая отправка прошла, а её результат не сохранился, повторная проверка может отправить тестовое сообщение ещё раз.

Завершённый запрос хранится ещё 24 часа после завершения, истёкший незавершённый — 24 часа после окончания срока. Затем он удаляется ежедневной очисткой. Канал продолжает работать после удаления запроса.

### Просмотр и изменение каналов

Любой участник может получить список и отдельный канал. Список включает активные и отключённые каналы, без удалённых и без пагинации; новые первыми, при одинаковом времени создания — дополнительная сортировка по идентификатору. Пустой список возвращается успешно.

При создании название канала берётся из выбранной Telegram-группы. Владелец может изменить название внутри K.Alert и включённость. При изменении название содержит от 1 до 100 символов после удаления пробелов по краям. Можно передать одно поле или оба; пропущенное сохраняется, пустой объект и null отклоняются.

Тип и Telegram-чат существующего канала изменять нельзя. Передача текущих значений возвращает текущий канал. Включение не выполняет тестовую отправку. В ответах API идентификатор чата передаётся строкой; секреты и внутренние настройки не возвращаются.

### Удалить канал

Владелец подтверждает удаление. Канал исчезает из обычного списка, история доставок сохраняется. Ранее созданные задания продолжают обрабатываться. Окно подтверждения явно сообщает, что ожидающие сообщения ещё могут прийти.

Повторное удаление уже удалённого канала возвращает успех без результата. Получение и изменение удалённого канала возвращают отсутствие канала.

При повторном подключении удалённого чата после тестовой отправки создаётся новая запись канала. Старые доставки связаны с прежней записью.

## Напоминания

### Список и просмотр

Любой участник команды, включая владельца, может получить список и отдельное неудалённое напоминание. Для просмотра не требуется наличие активных каналов.

Список использует пагинацию: `page` от 1 (по умолчанию 1), `pageSize` от 1 до 100 (по умолчанию 20). Фильтр `status` допускает `Active`, `Paused`, `Completed`; без фильтра показываются все неудалённые напоминания. `search` ищет часть названия без учёта регистра, удаляет пробелы по краям и ограничен 200 единицами UTF-16; пустое значение отключает поиск. Фильтры применяются совместно.

Новые напоминания идут первыми: `createdAt DESC`, затем `id ASC`. Общее число записей учитывает фильтры. Пустой результат или страница за пределами списка возвращаются успешно с пустым массивом.

Список и просмотр возвращают полный объект напоминания, версия передаётся строкой. Удалённые напоминания исключаются из этих методов; их срабатывания доступны через историю в пределах срока хранения. `Completed` означает завершение расписания, а существующие доставки ещё могут обрабатываться.

### Создать напоминание

1. Владелец или участник открывает вкладку «Напоминания» и нажимает «Создать напоминание».
2. Он указывает название, текст, дату первого срабатывания, местное время и часовой пояс.
3. Для повторяющегося напоминания он задаёт периодичность и интервал, например каждые две недели. При необходимости указывает дату окончания. Срабатывания в эту дату входят в расписание.
4. Сервис проверяет форму. После успешного сохранения показывает напоминание со статусом «Активно» и временем ближайшего срабатывания.

Сервис показывает ошибку рядом с полем, если название или текст пустые, расписание некорректно, первое срабатывание приходится на прошлое или текущий момент либо дата окончания раньше даты начала.

Для создания напоминания нужен хотя бы один активный канал. Если каналов нет, сервис сохраняет введённые данные в форме. Владельцу он показывает ссылку на настройки каналов, участнику предлагает обратиться к владельцу.

### Поля и формат сообщения

Название содержит от 1 до 200 единиц UTF-16 после удаления пробелов по краям, переносы строк в названии запрещены. Текст содержит от 1 до 3800 единиц UTF-16; пробелы и переносы сохраняются, значение только из пробельных символов отклоняется. Фронтенд и API считают длину одинаково: `string.Length` в C# и `.length` в JavaScript.

В Telegram отправляется одно обычное текстовое сообщение: название, пустая строка, текст. Разделитель — два `\n`. HTML и Markdown не обрабатываются. Максимальная длина при этих ограничениях — 4002 единицы UTF-16.

Контракт создания описан в [API](05-api-contracts.md#создать-напоминание). Автор, статус, ближайшее срабатывание, даты и версия задаются сервером. Начальная версия — 1, в JSON передаётся строкой.

### Календарные правила

- При повторении по месяцам исходное число сохраняется. Если такого числа нет, используется последний день месяца. Например, 31 января → 28 февраля → 31 марта.
- Ежегодное напоминание на 29 февраля в невисокосном году срабатывает 28 февраля, в високосном возвращается к 29 февраля.
- Дневные и недельные повторы сохраняют местное время выбранного часового пояса.
- Если при переводе часов вперёд указанное время отсутствует, срабатывание сдвигается на величину перевода. Например, при переходе с 02:00 на 03:00 время 02:30 превращается в 03:30. Следующий календарный повтор возвращается к исходному местному времени.
- Если при переводе часов назад время встречается дважды, создаётся одно срабатывание при первом наступлении этого местного времени. Правило применяется к разовым и повторяющимся напоминаниям.

### Изменение названия и текста

Любой участник команды может изменить название и текст неудалённого напоминания в состоянии Active, Paused или Completed. Расписание и статус сохраняются; активный канал для этого не требуется. Уже созданные срабатывания и доставки сохраняют свои снимки.

Клиент передаёт версию последнего прочитанного напоминания. API атомарно проверяет её при сохранении и возвращает конфликт при несовпадении. Каждое фактическое изменение записи, включая обновление ближайшего срока планировщиком, увеличивает версию на 1; изменения доставок её не меняют. Запрос с актуальной версией и неизменившимися значениями не меняет версию и время обновления. При конфликте интерфейс сохраняет ввод, получает актуальные данные и запрашивает повторное подтверждение пользователя.

### Изменение расписания

Любой участник команды заменяет расписание целиком с передачей версии. Первое срабатывание нового расписания должно быть строго в будущем. При фактическом изменении Active остаётся Active, Paused остаётся Paused, Completed переходит в Active. Для результата Active нужен активный неудалённый канал. Название, текст и автор сохраняются.

Уже созданные срабатывания и доставки продолжают обрабатываться. Ещё не созданные сроки старого расписания, включая просроченные необработанные, заменяются новым расписанием. Интерфейс поясняет это перед сохранением. Сохранение и планировщик координируются через БД: результат определяется порядком фиксации транзакций.

Проверка версии атомарна; при конфликте изменения не сохраняются. Фактическое изменение обновляет версию и время обновления. Запрос с актуальной версией и совпадающим расписанием возвращает текущий объект без пересчёта и смены статуса, даже для Completed; проверка будущего первого срока и активного канала в этом случае не требуется.

### Изменить, приостановить или удалить напоминание

| Действие | Поведение сервиса |
| --- | --- |
| Изменить | Сохраняет название, текст или расписание. При изменении расписания показывает пересчитанное ближайшее срабатывание. При конфликте правок сообщает о нём и предлагает открыть актуальную версию. |
| Поставить на паузу | Показывает статус «На паузе» и прекращает создавать новые срабатывания. |
| Возобновить | Продолжает исходное расписание с ближайшего будущего срабатывания. Даты, выпавшие на паузу, пропускаются. Если будущих дат нет, предлагает изменить расписание. |
| Удалить | После подтверждения убирает напоминание из основного списка и прекращает создавать новые срабатывания. История сохраняется. |

Уже созданные задания продолжают обрабатываться с текстом и назначениями, зафиксированными при срабатывании.

### Правила паузы, возобновления и удаления

Любой участник команды может приостановить, возобновить или логически удалить напоминание с проверкой версии. Пауза переводит Active в Paused и очищает NextOccurrenceAt, сохраняя исходное расписание; активный канал не требуется. Повторная пауза Paused возвращает текущий объект без изменений.

Возобновление Paused выбирает ближайший срок строго в будущем по исходной последовательности дат и переводит в Active. Нужен активный неудалённый канал. Все ещё не созданные сроки до возобновления, включая просроченные на момент паузы, пропускаются. Если будущих сроков нет, возвращается no_future_occurrences, напоминание остаётся Paused и интерфейс предлагает изменить расписание. Повторное возобновление Active возвращает текущий объект без пересчёта. Пауза и возобновление Completed возвращают invalid_reminder_state; для нового запуска меняют расписание.

Удаление Active, Paused или Completed устанавливает Deleted и очищает NextOccurrenceAt. Напоминание исключается из списка и просмотра, восстановление в первой версии отсутствует. Повторное удаление возвращает 204 после проверки доступа и формата параметров, без требования совпадения версии уже удалённой записи.

Проверка версии и переход атомарны. Для pause/resume версия проверяется также при запросе без изменения состояния; для повторного DELETE действует исключение выше. Фактический переход увеличивает версию и время обновления, повторное действие без изменений — нет. Уже созданные срабатывания и доставки продолжают обрабатываться, история хранится по общим правилам. Переходы координируются с планировщиком через БД: ранее зафиксированное срабатывание сохраняется.

## Срабатывания и история доставок

Для каждого срабатывания сервис создаёт отдельное задание для каждого чата, активного на момент создания заданий. Это правило действует и при обработке пропущенных сроков после сбоя. Если активных чатов нет, сервис записывает в историю «Пропущено — нет активных каналов» и продолжает расписание. После подключения канала отправка возобновляется со следующего срабатывания.

Владелец и участник могут открыть «Историю доставок» на странице команды. Для каждого срабатывания видны название напоминания, запланированное время и состояние доставки по каждому чату. История включает удалённые напоминания.

| Статус доставки | Что показывает сервис |
| --- | --- |
| Ожидает отправки | Задание готово к обработке. |
| Отправляется | Выполняется попытка отправки. |
| Доставлено | Telegram подтвердил отправку. Сервис показывает время подтверждения. |
| Ожидает повторной попытки | Произошла временная ошибка. Сервис показывает время следующей попытки. |
| Требует вмешательства | Сервис показывает причину, например отсутствие у бота доступа на отправку. После устранения причины владелец может возобновить доставку. |

Если сообщение получено только в одном из двух чатов, история показывает «Доставлено в 1 из 2 чатов». Повторная попытка выполняется для чата с ошибкой.

### Просмотр списка срабатываний

Любой участник команды видит историю всей команды или выбранного напоминания, включая удалённые, в пределах срока хранения. Список поддерживает пагинацию и совместные фильтры reminderId, scheduledFrom и scheduledTo. Обе границы включительны и относятся к запланированному ScheduledAt; равные границы допустимы. В API моменты передаются в UTC с Z, интерфейс переводит местные даты в UTC. Сортировка — ScheduledAt по убыванию, затем Id по возрастанию.

Для каждого срабатывания показываются снимки названия/текста, запланированное время, время создания и текущие счётчики доставок по шести состояниям. Полностью доставленным считается только срабатывание с хотя бы одной доставкой и всеми Sent. Срабатывание без доставок отмечается пропущенным из-за отсутствия активных каналов. Blocked требует вмешательства владельца. Сводка вычисляется без отдельного хранимого статуса срабатывания.

### Подробности срабатывания

Любой участник команды видит снимок сообщения, сводку и доставки по чатам без пагинации. Для доставки показываются текущее название канала, тип и адрес из снимка назначения, состояние, число выдач на попытку, время следующей попытки, подтверждённой отправки и последнего изменения, последняя безопасная ошибка и внешний идентификатор сообщения. Список отсортирован по времени создания и идентификатору; сводка соответствует тому же состоянию данных.

Удаление напоминания или логическое удаление канала не скрывает сохранившуюся историю. Для срабатывания без доставок возвращаются пустой массив и нулевая сводка. Токены захвата, срок захвата, служебные настройки и секреты пользователю не передаются. Отдельный журнал всех попыток в первой версии не добавляется.

### Восстановление после сбоя

- Сохранённые задания продолжают обрабатываться после восстановления. Успешно подтверждённые доставки в другие чаты не повторяются из-за ошибки в одном канале.
- Если сервис был недоступен в момент срабатывания и ещё не создал задания, после восстановления он обрабатывает **каждое** пропущенное срабатывание по действовавшему расписанию. В истории сохраняются исходное запланированное время и время подтверждения доставки по каждому чату.

### Повторные попытки

После временной ошибки следующая попытка назначается через 1 минуту, затем через 5, 15, 30 и 60 минут. Последующие попытки назначаются каждый час. Каждый интервал отсчитывается от завершения соответствующей неудачной попытки. Попытки продолжаются до успеха, отмены или ошибки, требующей вмешательства.

### Хранение истории

История хранится 90 дней после завершения срабатывания. Для срабатывания с доставками отсчёт начинается после завершения последней доставки, когда все задания находятся в статусах `Sent` или `Cancelled`. При наличии ожидающей, выполняемой или заблокированной доставки история сохраняется до её завершения.

Для срабатывания, пропущенного из-за отсутствия активных каналов, срок отсчитывается от его создания. Очистка запускается раз в сутки и удаляет срабатывание вместе со всеми его доставками. Само напоминание и его расписание сохраняются. В интерфейсе истории указан срок хранения.

## Сквозная проверка первой версии

1. Новый пользователь самостоятельно регистрируется, создаёт команду, подключает два групповых чата Telegram и приглашает коллегу.
2. Коллега регистрируется по пути из приглашения, подтверждает вступление и создаёт периодическое напоминание с первым срабатыванием в будущем.
3. При первом срабатывании оба чата получают сообщение. В истории видно запланированное время и два подтверждённых результата доставки.
4. Если сервис недоступен в течение двух следующих срабатываний, после восстановления в истории появляются оба с исходными запланированными временами. Доставка выполняется для каждого срабатывания.
